### 2.2 设计 ↔ 现有代码

**代码基线：** `src/models/types.ts:SSHConfig` 含 20+ 字段（含 `algorithms, pty, allowedLocalPaths, commandTemplate` 等），`src/cli/command-line-parser.ts:CommandLineParser` 含 `normalizeConfig`（路径展开、`~`、`port` 解析、`whitelist/blacklist` 的 `|` 分隔 vs CLI `,` 分隔、`allowedRemotePaths` 的 POSIX 校验）、`src/core/mcp-server.ts:SshMcpServer` 为 `McpServer + StdioServerTransport` 单例模式、`src/services/ssh-connection-manager.ts` 75170字节含 `exec/shell` 双模式、`scripts/build.js` 仅 `tsc`。

**发现的不一致：**

#### [高] R1 — Tauri sidecar 形态与现有构建链冲突
- **现状：** `scripts/build.js` 仅 `tsc → build/index.js`，无 sidecar。`package.json` 为 `type: module` 纯 JS，依赖 `ssh2`（纯 JS）+ `zod`。设计 §7 要求 `esbuild` 单文件到 `src-tauri/sidecars/ssh-mcp-server-node`，再 `externalBin` 声明。但 Tauri 的 `externalBin` 期望**原生可执行文件**，而 `esbuild` 产出是 `.js`，需 Node 解释器。Plan Task 10 的 `tauri.conf.json` 写法在 `cargo tauri dev` 时会因找不到二进制而失败。
- **影响：** P3 无法构建。
- **建议改动：** Spec §7 + Plan Task 10 明确二选一：**A) sidecar 为 JS + Tauri `shell` 插件 `spawn("node", ["build/server/index.js"])`**（需用户本机有 Node，适合 dev） vs **B) 用 `pkg`/`@yao-pkg/pkg` 或 Node SEA 打包为单二进制**（适合 release）。首版推荐 **A dev + B release** 双路径，并补 `scripts/build-sidecar.js` 的分支逻辑。

#### [高] R2 — better-sqlite3 原生模块与 esbuild/SEA 不兼容
- **现状：** `better-sqlite3` 需 `node-gyp` 编译，`esbuild --bundle` 会将其视为 external，`pkg` 也无法打包原生 `.node` 文件。现有 `package.json` 无原生依赖，CI 为纯 `npm install`。
- **影响：** 审计功能在 Tauri sidecar 二进制中会 `Cannot find module better-sqlite3.node`。
- **建议改动：** Spec §5/Plan Task 5 补充：**审计 DB 选型二选一**：保留 `better-sqlite3` 则 sidecar 必须以 `node + 源码` 分发（不打包），或改用纯 JS `sql.js`/`@sqlite.org/sqlite-wasm`/`sqlite`（`sqlite3` 的 wasm 版）以支持单文件打包。推荐首版用 `better-sqlite3` + **不打包**（Tauri 安装包内带 `node_modules`），Plan Task 11 的 `cargo tauri build` 前执行 `npm ci --omit=dev` 并配置 `tauri.conf.json:resources`。

#### [中] R3 — ConfigStore 与 CommandLineParser.normalizeConfig 重复且语义分裂
- **现状：** `CommandLineParser.normalizeConfig` 负责 `port` 转 number、`privateKey` 的 `path.resolve(expandHomePath)`、`allowedRemotePaths` 的 `path.posix.isAbsolute` 校验、`whitelist/blacklist` 的 `|` vs `,` 双兼容、`algorithms/keepalive` 等默认值。设计 §4.2 称 `connections` 复用 `SSHConfig`，但 Plan Task 1 的 `admin-types.ts:ConnectionSchema` 仅校验 `name/host/port/username`，丢失 15+ 字段的校验与路径归一化。
- **影响：** Admin API 写入的 `privateKey: "~/key"` 不会被展开，`allowedRemotePaths: "relative/path"` 不会报错，与 CLI 行为不一致。
- **建议改动：** Spec §4.2 补一句“**Admin API 入站必须经 `CommandLineParser.normalizeConfig` 归一化后落盘**”，Plan Task 1/3 的 `POST /admin/api/connections` 显式调用 `CommandLineParser.normalizeConfig`（需将其从 `private` 改为 `public` 或抽 `normalizeSSHConfig` 工具），并补单元测试：`POST { privateKey: "~/id_rsa" }` 后 `GET` 返回 `path.resolve(os.homedir(), "id_rsa")`。

#### [中] R4 — 端口语义冲突
- **现状：** 现有 CLI 的 `--port/-p` 指 **SSH 远端端口**（默认 22），而设计 §2.2 的 `--admin-port` 指 **Admin HTTP 端口**（默认 61823）。`package.json` 的 `bin` 为 `build/index.js`，用户 `npx ssh-mcp-server --port 2222` 的含义会被混淆。Plan Task 2 的 `src/index.ts` 分支 `if (process.argv.includes("--admin"))` 未处理 `--admin-port` 无 `--admin` 的情况。
- **建议改动：** Spec §2.2 明确“**SSH 端口仍为 --port/-p，Admin 端口为 --admin-port，且两者可共存**”，`CommandLineParser` 新增 `adminPort` 字段与 Spec 的优先级链解耦，Help 文案分两段。Plan Task 2 补测试：`--host 1.1.1.1 --port 2222 --admin-port 61823` 同时生效。

#### [中] R5 — 一键注册的 scope 未定义
- **现状：** 设计 §5.2 `POST /admin/api/system/register-mcp` 未定义 `scope=user|project|local`，也未说明 `~/.claude.json` 的 `mcpServers` 与项目级 `.mcp.json` 的合并策略（覆盖/改名/取消在 UI 提示，但 API 未暴露冲突检测）。
- **建议改动：** Spec §5.2 补 `register-mcp` 的请求/响应契约：`{ client: "claude"|"cursor"|"cline", scope: "user"|"project"|"local", serverName?: string } → { ok, path, conflict: boolean }`，前端在 `conflict=true` 时弹窗。Plan Task 9 的测试补 `conflict` 分支。

#### [低] R6 — 前端选择未锁定
- **现状：** 设计 §6 写“Ant Design（或 shadcn，二选一，首版定 AntD）”，但 Plan Task 7 未锁定，导致 Task 7/8 的测试与实现可能分叉。
- **建议改动：** Spec §6 删“或 shadcn”，锁定 **Ant Design 5**。
